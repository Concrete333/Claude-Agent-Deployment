# Claude-native adapter trial, A and D — 10 September 2026

**Delegating a specified implementation to one Opus 5 `low` builder cost 18.3% less than Fable 5.1 solo, both passed every check, and this time the orchestrator reviewed the source.** This reproduces, on Claude models, the shape the Codex team found on the same task (18.4% and 10.4% savings): move the writing to the cheap model, keep a capable coordinator on acceptance. One run per arm.

Post-hoc probes, run unchanged against both saved submissions after grading: the two JSONL bare-CR cases the Codex team's conditional-read worker initially got wrong (a whitespace-only line containing CR; CR as JSON whitespace inside one physical line), CR-separated objects (must fail), and a 150,000-character CSV memo with quotes and CRLF. Both passed all four. The JSONL cases are not in the frozen fixture; the CSV case duplicates coverage the version-two visible fixture already has.

## What each arm did

A read the task, helpers, example, checker and fixtures, wrote `_shared.py` and the six adapters in one pass, ran the checker (146/146 first time), ran a one-line sanity script, wrote 17 tests and ran them. No corrections. Output 18,102 tokens (6,747 thinking).

D's orchestrator read `SKILL.md` and `TASK.md`, globbed the tree, dispatched one `builder` call, then did its own acceptance: re-ran the checker and the tests, verified all protected hashes, and read `_shared.py`, `statement_xml.py`, `batch_json.py`, `events_jsonl.py`, `fixed_width.py` and `euro_csv.py` (not `bank_csv.py`), plus one grep. It reported the process-global `csv.field_size_limit` change as an unresolved thread-safety risk. No correction was requested. The worker (transcript: `claude-opus-5`, effort `low`) wrote the seven files, failed the checker once, made four edits to `_shared.py` and `statement_xml.py`, passed, then wrote and ran 39 tests.

## Against the prose result

Same models, same arms, opposite verification behaviour. On the prose task the orchestrator ran a checker and stopped. Here, with the amended skill (which now says a mechanical checker is not verification and the sources or the code must be read), it read most of the delivered code and ran every check itself. Two differences could explain that and the design cannot separate them: the skill text changed between the runs, and code review is a more natural instinct for a coding agent than rereading fifty prose threads. A prose rerun under the amended skill would tell.

Taken together with the Codex adapter pairs, the picture is consistent: on a specified component with executable checks, one cheap owner plus coordinator source review has now saved 10% to 18% in three of three solo-versus-team pairs across two vendors (the Codex team's fourth pair compared two skill versions, both delegating). All passed their frozen checks; the first Codex pair and its reference later failed a large-CSV probe, so "no quality loss" is established only for the two pairs graded on the version-two fixture. On read-dominated interpretation work it has saved money only by skipping verification, and no cheap verifier has qualified.

Both submissions share the Codex conditional-read run's limitation: the CSV reader raises and restores the process-global field-size limit. D's orchestrator flagged it; A's did not mention it. The contract says nothing about concurrency, so neither was penalised.

## Limits

One run per arm, fixed order, uncontrolled sampling and cache state, a fixture the evaluator knows, no C arm (spontaneous routing), and a task the Codex team designed to favour context-isolating delegation. Both arms passed first time, so nothing here measures how the two workflows handle a correction loop or a coordinator-found defect; the Codex pairs are the only evidence on that, and there review earned its cost. The 18.3% is one sample.
